# PDF 전용 포트폴리오와 덩어리 중심 구조 설계

- 날짜: 2026-11-17
- 상태: 사용자 승인 대기
- 계획 범위: 0단계(리팩터링)와 1단계(PDF)를 먼저 계획한다. 2단계(웹)는 이 문서에 방향과 완료 기준을 정해 두고, 시작할 때 계획한다.

## 1. 무엇을, 왜

포트폴리오 PDF를 "표지 한 쪽 + 덩어리 하나에 한 쪽"인 전용 문서로 바꾼다. 여기에 맞춰 사례 데이터, 그림 연결, 검사를 덩어리 단위로 다시 짠다. 웹 사례 페이지는 2단계에서 같은 두 깊이 구조를 따른다.

이 문서의 용어는 다음과 같다.

| 용어 | 뜻 |
|---|---|
| 덩어리 | 문제 해결 사례 하나. 제목, 그림, 문제·해결·결과로 이뤄진다. 지금 코드의 `CaseProblem`이다 |
| 요점 | 문제 원인·해결 과정·결과마다 3개 이상 쓰는 짧은 글. PDF에 나오고, 2단계부터 웹 표면에도 나온다 |
| 자세한 글 | 지금 있는 문단 글. 웹에서 "자세한 과정"으로 보인다 |
| 쪽 상자 | PDF의 한 쪽을 그리는 210×297mm 상자 |
| 종이 범위 | export 문서에만 적용하는 색과 글자 크기 규칙의 범위 |

이렇게 바꾸는 이유는 네 가지다.

1. 지금 PDF는 훑을 수 없다. 29쪽, 약 2만 자이고 본문에 강조가 없으며 결과는 문제마다 끝에 있다. 서류 검토자는 포트폴리오를 1분 안팎으로 훑는다(2026-11-17 조사).
2. 사용자가 따르기로 한 가이드(생각등대, 『개발자를 위한 이력서 포트폴리오 완벽 가이드 2』, 2026.02)는 덩어리를 "제목, 그림, 문제, 해결, 결과"로 짜고 문제·해결·결과를 각 3줄 정도로 쓰라고 한다.
3. 지금의 긴 글은 지우지 않는다. 사이트 방문자가 깊이 읽는 글이고, 사용자가 다시 보는 기록이며, 면접 답변의 근거다.
4. 그래서 짧은 글과 긴 글 두 벌이 생기는데, 두 글이 어긋나면 안 된다. 특히 숫자는 그동안 실제 빌드와 저장소로 여러 번 검증해 고쳐 온 영역이다.

독자는 셋이다.

| 독자 | 보는 것 | 읽는 방식 |
|---|---|---|
| 서류 검토자 | PDF | 약 1분 동안 훑는다 |
| 면접관, 사이트 방문자 | 웹 사례 페이지 | 필요한 만큼 읽는다 |
| 사용자 본인 | 웹 사례 페이지 | 이직할 때마다 다시 읽는다 |

## 2. 목표

### 이루려는 것

1. PDF는 표지 1쪽과 덩어리마다 정확히 1쪽으로 이뤄진다. 지금 고른 덩어리가 9개이므로 10쪽이다.
2. 덩어리 쪽은 어느 쪽을 펼쳐도 그 쪽만으로 이해된다. 프로젝트 정보를 쪽마다 반복한다.
3. 요점과 자세한 글은 데이터에서 붙어 있어서, 한쪽을 고칠 때 다른 쪽이 함께 보인다.
4. 글이 쪽 상자를 넘치면 PDF가 만들어지지 않는다. 줄 수와 그림 크기는 PDF를 열어 눈으로 확인한다.
5. 브라우저에서 `/export`를 열면 PDF와 같은 모습이 보인다.
6. 데이터를 새 모양으로 옮기는 동안 기존 글의 글자는 하나도 바뀌지 않는다.
7. 2단계에서 웹 사례 페이지는 요점을 먼저 보여 주고, 자세한 글은 그 아래 "자세한 과정"으로 둔다.

### 하지 않는 것

- 공고마다 다른 PDF를 여러 벌 만드는 구조. 지금은 목록 하나만 둔다. 나중에 목록을 하나 더 만들고 PDF를 한 번 더 뽑으면 되는 모양만 유지한다.
- 자세한 글의 내용 보강(면접 꼬리 질문 점검)과 재직 중인 회사 사례의 공개 수준 점검. 사용자가 뒤로 미룬 별도 작업이다. 요점 3개를 채우는 데 필요한 `content-form-unify`의 보강만 예외다(8절).
- 이력서 수정.
- 글을 Markdown 파일로 옮기는 것, 숫자를 등록표에 두고 글에 끼워 넣는 것, 덩어리마다 웹 페이지를 따로 두는 것, 조판 도구를 바꾸는 것(5절 참고).
- `data/projects.ts`를 프로젝트별 파일로 나누는 것.
- 사이트 페이지를 브라우저에서 직접 인쇄했을 때의 모양. 사용자가 인쇄 전용 코드를 모두 지워도 된다고 정했다(6.8절).
- 새 검사를 여러 개 만드는 것. 이 저장소의 목적은 이직용 포트폴리오의 내용이고, 사용자가 검사를 줄이기로 했다(6.7절).

### 실패로 보는 것

- 자세한 글이 줄거나 문구가 바뀐다.
- 요점에 자세한 글에 없는 사실이나 숫자가 들어간다.
- 한 쪽에 넣으려고 그림이나 글자가 읽기 어려울 만큼 작아진다.
- 넘친 글이 잘린 채로 PDF가 배포된다.
- 웹과 PDF의 요점이 서로 다른 문구가 된다.

## 3. 지금 상태

- **데이터:** `data/projects.ts`(606줄)의 `Project.caseStudy.problems[]`에 있다. 문제는 `title`, `problem`, `solution`, `result`, `visual?`을 가진다. 본문 세 필드는 문단을 `\n\n`으로 이은 문자열 하나다. 사례가 있는 프로젝트는 7개, 문제는 16개다.
- **그림:** `visual`의 타입은 `diagram`·`code`·`metrics` 세 종류지만 데이터에서 쓰는 것은 `diagram` 15회뿐이다. 그림 파일은 `public/diagrams/<id>.drawio.svg`이고, 대체 텍스트는 `components/case-study/diagrams.ts`의 `DIAGRAMS` 등록표에, 그림 설명은 데이터에 있다. 그림 15개는 문제 15개와 하나씩 짝이고 파일 이름이 곧 id다. 그림이 없는 문제는 촉각 그래픽 편집 도구의 첫 접속(LCP) 사례 하나다.
- **PDF:** `app/export/page.tsx`가 웹 상세 컴포넌트 `CaseStudyBody`를 그대로 그리고 `scripts/generate-pdf.mjs`가 Playwright로 인쇄한다. 실을 프로젝트는 `data/project-lists.ts`의 `PDF_PROJECT_IDS`(6개)가 정한다. 인쇄 모양은 `app/globals.css`의 `@media print` 규칙, 컴포넌트의 `print:` 클래스, 프로젝트별 `@page` 규칙으로 맞춘다.
- **사이트 틀:** 메뉴, 본문 폭, 푸터가 루트 레이아웃(`app/layout.tsx`)에 있어서 `/export`도 그 안에 그려진다. 404(`app/not-found.tsx`)도 루트 레이아웃이 그리는 틀에 기댄다.
- **검사:** `lib/content-check.ts`의 `validateCaseStudy`가 빈칸과 백틱 짝을 보고, `lib/data.test.ts`가 목록과 PDF 사례의 완성도를 본다. 사례 전체의 완성도는 `pnpm check:content`(`data/content.check.ts`)가 따로 보는데, CI에서 실패해도 배포는 계속된다.
- **배포:** main에 push하면 `.github/workflows/deploy.yml`이 `pnpm test`를 돌린 뒤 `pnpm run build`(사이트와 PDF)로 만들어 GitHub Pages에 올린다. PDF는 사이트 첫 화면의 "포트폴리오 PDF" 버튼으로 내려받는 `portfolio.pdf`다. PDF 생성이 실패하면 사이트 배포도 멈춘다.

## 4. 제약

- Next.js 16.4.6, `output: "export"`, `trailingSlash: true`, 운영 `basePath: "/portfolio"`를 유지한다. `AGENTS.md`에 따라 코드를 쓰기 전에 `node_modules/next/dist/docs/`의 해당 문서를 읽는다.
- 의존성을 새로 더하지 않는다.
- Biome, vitest, pnpm을 쓴다. 사이트 문구는 한국어 존댓말 평서문이다.
- 저장소와 사이트는 공개다.
- 글에는 사용자가 정한 규칙이 있다.
  - 데이터에 없는 사실과 숫자를 만들지 않는다.
  - 글을 줄이거나 문구를 바꾸려면 먼저 제안하고 승인받는다. 모든 수정에 근거를 붙인다.
  - 일부만 잘라 좋아 보이는 숫자는 쓰지 않는다.
  - 수는 "읽는 대로" 적는다(8절의 수 표기 규칙).
- 커밋은 사용자가 요청할 때만 한다. 지금 브랜치는 `content/saramin-case-study`다. 이 작업을 어느 브랜치에서 할지는 계획을 세울 때 사용자에게 확인한다.

## 5. 검토한 구조

| | 구조 | 얻는 것 | 치르는 것 |
|---|---|---|---|
| A | 지금 구조에 덧붙이기. 문제 객체에 `brief`를 더하고, 웹 페이지를 인쇄 스타일로 찍고, 쪽이 넘치면 빌드를 실패시킨다 | 가장 적게 바뀐다 | 웹 컴포넌트 안의 인쇄 분기가 남는다. 한 쪽에 맞는지는 글을 써 보고 실패해 봐야 안다 |
| **B (선택)** | 덩어리를 단위로 다시 짠다. 데이터는 섹션마다 요점과 자세한 글을 묶고, PDF는 처음부터 A4 쪽 상자로 그린다 | 쪽 수가 구조로 정해진다. 요점과 근거가 붙는다. 그림 연결이 단순해진다 | 데이터 모양이 바뀌어 문제 16개와 이를 읽는 파일 11개를 옮긴다 |
| C | B에 더해 글을 Markdown 파일로 옮긴다 | 글 쓰기가 편하고 GitHub에서 바로 읽힌다 | 타입 검사를 잃는다. 파서와 그 테스트가 생긴다 |

사용자는 B를 골랐다. 사용자는 기존 방향이 최선의 구조라는 전제를 두지 말라고 했고, B는 요구사항(1분 훑기, 한 쪽에 한 덩어리, 두 글이 어긋나지 않기, 긴 글 보존)에서 출발한 구조다. C를 고르지 않은 이유는 덩어리 16개가 모두 같은 틀이라 타입 검사가 더 쓸모 있고, 나중에 Markdown으로 옮기려면 객체를 파일로 쓰는 스크립트 한 번이면 되기 때문이다.

검토하고 뺀 것은 다음과 같다.

- **Typst, react-pdf 같은 조판 도구:** draw.io 그림의 글자(foreignObject)를 브라우저만 그린다.
- **숫자 등록표와 치환:** 글이 틀 문법으로 바뀌어 읽고 쓰기 어려워진다.
- **덩어리마다 웹 페이지:** 한 프로젝트의 맥락이 페이지 여러 개로 흩어진다.
- **웹과 PDF가 함께 쓰는 큰 덩어리 컴포넌트:** PDF 쪽은 그림이 자리에 맞춰 줄어들고 웹은 눌러서 확대하는 그림이라, 한 컴포넌트에 넣으면 인쇄 분기가 다시 생긴다.

B는 일곱 관점(PDF·인쇄, Next.js 구조, 타입·테스트, 글 쓰는 사람, 서류 검토자, 접근성, 비용)으로 검토해 여섯 곳을 고쳤고, 6절은 고친 결과다. 고친 곳은 그림 배치(6.4), 404 페이지(6.5), 종이 범위(6.4), 표지 그림(6.4), 작업 순서(7절)다. 여섯째였던 요점 타입 표기는 검사를 줄이면서 뺐다(6.7).

## 6. 설계

### 6.1 데이터 모델

`app/types/project.ts`를 이렇게 바꾼다.

```ts
// 덩어리 id. 그림 파일 이름(public/diagrams/<id>.drawio.svg), 웹 앵커(#id), PDF 목록이 모두 이 값을 쓴다.
export type ChunkId =
  | "blue-green-deploy"
  | "bff-auth-flow"
  | "msw-mock-switch"
  // … 아래 표의 16개
  ;

export interface ChunkSection {
  // PDF와 (2단계부터) 웹 표면에 보이는 짧은 글. 개수는 8절의 규칙을 따른다. 2단계가 끝나면 필수로 바꾼다.
  points?: string[];
  // 자세한 글. 문단마다 한 항목이다.
  detail: string[];
}

export interface ChunkFigure {
  alt: string;
  caption: string;
}

export interface Chunk {
  id: ChunkId;
  title: string; // 웹과 PDF가 같이 쓴다
  figure?: ChunkFigure;
  problem: ChunkSection;
  solution: ChunkSection;
  result: ChunkSection;
}

export interface CaseStudy {
  summary: string;
  background: string;
  team: string;
  chunks: Chunk[]; // 지금의 problems
}
```

덩어리 id는 다음과 같다. 그림이 있는 15개는 지금의 다이어그램 id를 그대로 쓴다.

| 프로젝트 | 덩어리 id (데이터 순서) |
|---|---|
| `enterprise-legal-management` | `blue-green-deploy`, `bff-auth-flow`, `msw-mock-switch` |
| `external-settlement-system` | `settlement-domain-config`, `s3-cache-policy` |
| `ip-management-system` | `e2e-regression-baseline`, `ai-agent-guardrails`, `vite-rolldown-chunks`, `content-form-unify` |
| `ats-monitoring-system` | `nextauth-token-refresh` |
| `design-system` | `design-token-pipeline`, `chromatic-visual-test` |
| `wysiwyg-editor` | `ckeditor-virtual-scroll`, `a11y-export-check` |
| `tactile-graphics-editor` | `first-load-lcp`(새 id, 지금은 그림 없음), `fabric-group-batch-add` |

옮기는 규칙은 다음과 같다.

- `problem`, `solution`, `result` 문자열은 빈 줄(`\n\n`) 기준으로 나눠 `detail` 배열에 넣는다. 글자는 바꾸지 않는다.
- `visual.caption`은 `figure.caption`으로, `DIAGRAMS[id].alt`는 `figure.alt`로 그대로 옮긴다.
- 화면에 보이는 "핵심 문제" 같은 라벨은 바꾸지 않는다. 이름을 바꾸는 것은 코드뿐이다.
- 요점은 한 덩어리의 세 섹션에 모두 쓰거나 모두 쓰지 않는다.

### 6.2 그림 연결

- 그림 파일 경로는 덩어리 id에서 만든다. `public/diagrams/<id>.drawio.svg`다. 경로를 만드는 곳은 한 군데에만 둔다.
- 다음은 지운다. 근거는 데이터에서 쓰는 곳이 0곳이거나, 위 규칙으로 대체되기 때문이다.

| 지우는 것 | 근거 |
|---|---|
| `CaseVisual` 타입의 `code`, `metrics` 종류 | 데이터에서 0회 사용 |
| `components/case-study/code-block.tsx`, `metrics-card.tsx`, `case-visual.tsx` | 위 두 종류만을 위한 컴포넌트와 분기 |
| `DiagramId` 타입, `components/case-study/diagrams.ts`의 `DIAGRAMS` | `ChunkId`와 `figure`가 대신한다 |

- 웹의 그림 컴포넌트(`diagram-view.tsx`, 눌러서 확대)는 남기고 덩어리의 `id`와 `figure`를 받게 바꾼다.

### 6.3 PDF 목록

`data/project-lists.ts`의 `PDF_PROJECT_IDS`를 `PDF_CHUNK_IDS: ChunkId[]`로 바꾼다. 적힌 순서가 PDF 순서다. 사용자가 고른 9개와 순서는 다음과 같다. 프로젝트 순서는 지금 PDF와 같다.

1. `blue-green-deploy`
2. `bff-auth-flow`
3. `e2e-regression-baseline`
4. `content-form-unify`
5. `settlement-domain-config`
6. `design-token-pipeline`
7. `ckeditor-virtual-scroll`
8. `first-load-lcp`
9. `fabric-group-batch-add`

`lib/projects.ts`의 `getPdfProjects`는 `getPdfChunks`로 바꾼다. 목록 순서대로 `{ project, chunk }`를 돌려준다. 목록의 id에 해당하는 덩어리가 없거나, 그 덩어리에 그림이나 세 섹션의 요점이 없으면 던진다. 돌려주는 덩어리의 타입은 그림과 요점이 반드시 있는 타입이어서 PDF 쪽 코드가 "없을 수도 있음"을 다루지 않아도 된다. `HOME_PROJECT_IDS`와 `getCaseStudiesByIds`는 그대로 둔다.

### 6.4 PDF 문서

`/export`는 웹 페이지를 인쇄한 것이 아니라, 처음부터 A4 쪽 상자로 그린 문서다.

**쪽 상자**

- 쪽마다 210×297mm 상자 하나다. 안쪽 여백을 두고, 세로로 쌓는 배치이며, 상자마다 쪽을 나눈다. 상자 높이가 고정이라 글이 넘쳐도 쪽 수는 늘지 않고, 넘친 부분은 PDF에서 잘려 나간다. 그래서 넘침은 6.7의 확인이 막는다.
- `@page { size: A4; margin: 0 }`을 쓰고, PDF는 CSS의 쪽 크기를 따르게 만든다(`preferCSSPageSize`). 스크립트의 여백 옵션은 없앤다.
- 쪽 여백 상자(`@bottom-left` 등)와 프로젝트별 `@page` 규칙은 쓰지 않는다. 꼬리말은 쪽 상자 안에 직접 그린다.
- 화면에서는 쪽 상자 사이에 간격을 둬 낱장으로 보이게 한다. 이 꾸밈은 화면에서만 적용한다. 이것 말고는 화면과 인쇄에서 다르게 동작하는 규칙을 두지 않는다. 그래야 브라우저에서 본 모습이 PDF와 같다.

**표지 (1쪽)**

- 이름, "프론트엔드 포트폴리오", 레고 그림, 사이트 주소(링크)를 둔다. 소개 문단, 경력, 연락처, 목차는 넣지 않는다. 이력서와 겹치기 때문이다.
- 레고 그림은 움직이는 `HeroLego`가 아니라 정적인 장면(`components/portfolio/hero-lego/scene.tsx`의 `SCENE`)만 그린다. 흰 바탕에 두고, 이름보다 작고 덜 두드러지게 한다. 보조 기술에는 장식으로 숨긴다. `SCENE`을 그리려면 `hero-lego.tsx`가 불러오는 스타일 두 개(`components/iso/iso.css`, `hero-lego.css`)가 함께 필요하다.
- 표지에는 꼬리말을 두지 않는다.

**덩어리 쪽 (2쪽부터)**

위에서 아래로 다음 순서다.

1. 머리말: 프로젝트 이름, 회사, 기간, 팀. 그 아래 주요 기술(`getMainTech` 그대로, 최대 5개). 작은 글씨다. 모든 덩어리 쪽에 반복한다.
2. 제목: 덩어리의 `title`. 사이트의 그 덩어리 위치로 가는 링크이지만 겉모습은 보통 제목이다. 주소는 `PROFILE.siteUrl` + `projects/<프로젝트 id>/#<덩어리 id>`다.
3. 그림과 그림 설명. 그림에는 `figure.alt`를 대체 텍스트로 단다.
4. 요점. 칸 이름은 가이드를 따라 "문제 원인", "해결 과정", "결과"다.
5. 꼬리말: 가운데에 "쪽 번호 / 전체 쪽 수"만 둔다(사용자 결정, 2026-11-17). 쪽 번호는 표지를 1로 세고, 목록에서의 순서로 계산한다. 쪽 상자의 맨 아래에 붙는다.

**그림 배치**

- 그림은 원래 비율대로 본문 폭에 맞춰 제목 밑에 놓는다. 자리가 모자랄 때만 비율을 지키며 줄어든다. 남는 높이는 요점과 꼬리말 사이에 모인다.
- 시험에서 통한 방법은 이렇다. 그림 상자에 그림의 원래 비율(`aspect-ratio`)을 주고 줄어들 수 있게 두며, 그 안의 그림은 상자에 맞춰 비율을 지키게 한다(`object-fit: contain`). 꼬리말은 `margin-top: auto`로 바닥에 붙인다.

**종이 범위**

- export 문서의 색과 글자 크기는 `@media print`가 아니라 문서 범위(예: 맨 바깥 요소의 클래스)에 정의한다. 그래야 브라우저에서 본 모습과 PDF가 같다.
- 지금 `@media print`에 있는 것 중 옮길 것은 종이 색 토큰(흰 종이, 남색 잉크, 진한 테두리), 본문 11pt, 그림 설명 9.5pt, 인라인 코드 모양이다.

**그 밖**

- PDF 책갈피에는 표지의 이름과 덩어리 제목 9개가 나오면 된다. 지금처럼 태그 있는 PDF로 만든다.
- 문서 제목(`포트폴리오 | 이성준`)과 파일 경로(`out/portfolio.pdf`)는 그대로다.
- 개발 중에는 `pnpm dev`로 `/export/`를 열어 본다.

### 6.5 사이트 틀 분리

- 메뉴, 본문 틀(`<main id="main-content">`), 푸터, 본문 바로가기 링크를 껍데기 컴포넌트 하나로 묶는다.
- 사이트 페이지(홈, `archive`, `projects/[id]`)를 `app/(site)/` 그룹으로 옮기고, 그 그룹의 레이아웃이 껍데기를 쓴다. 주소는 바뀌지 않는다.
- 루트 레이아웃에는 `<html>`, `<body>`, 글꼴, 메타데이터만 남긴다.
- `app/export/`는 그룹 밖에 두어 빈 종이에서 시작한다.
- `app/not-found.tsx`는 루트에 남기고 껍데기로 감싼다. 루트의 404는 맞는 경로가 없는 모든 주소를 맡기 때문에 그룹 안으로 옮기지 않는다.
- `app/types/`는 옮기지 않는다.

### 6.6 웹 사례 페이지

**1단계**에서는 덩어리 블록에 `id`(덩어리 id)만 단다. PDF 제목의 링크가 도착할 곳이다. 고정된 메뉴에 가려지지 않아야 하는데, 전역 스타일에 이미 `scroll-padding-top`이 있어서 따로 할 일은 없을 것이다. 실제로 가려지지 않는지만 확인한다. 화면의 나머지는 바꾸지 않는다.

**2단계**에서는 덩어리 블록을 이렇게 바꾼다.

```
제목
그림 (눌러서 확대)
문제 원인   • … • …
해결 과정   • … • … • …
결과        • … • …
▸ 자세한 과정      ← 누르면 지금의 "문제 확인 / 해결 과정 / 결과" 문단이 펼쳐진다
```

- 요점을 그리는 작은 컴포넌트 하나를 PDF와 웹이 같이 쓴다. 같이 쓰는 컴포넌트는 이것뿐이다.
- "자세한 과정"은 자바스크립트 없이 동작하는 `<details>`로 만든다. 기본은 접힌 상태로 만들고, 실제 화면을 사용자에게 보여 준 뒤 접을지 펼칠지 확정한다.
- 2단계를 시작하려면 나머지 덩어리 7개의 요점이 필요하다. 다 채우면 `points`를 필수로 바꾸고, 요점 없이 문단만 그리는 경로를 지운다.
- 요점이 일부 덩어리에만 있는 상태로 웹을 바꾸지 않는다. 사례 페이지 7개 중 5개에서 두 모양이 섞이기 때문이다.

### 6.7 검사

검사는 꼭 필요한 것만 둔다. 이 저장소의 목적은 이직용 포트폴리오의 내용이고, 사용자가 검사에 시간을 쓰지 않기로 했다(2026-11-17).

**하는 것**

- 지금 있는 테스트를 새 데이터 모양에 맞게 옮긴다. `validateCaseStudy`의 빈칸과 백틱 짝, `lib/data.test.ts`와 `lib/projects.test.ts`의 목록 테스트가 해당한다. 새 규칙은 더하지 않는다.
- `getPdfChunks`는 6.3대로, 그릴 수 없는 덩어리가 목록에 있으면 던진다. 빌드가 거기서 멈춘다.
- 새로 만드는 확인은 하나다. `scripts/generate-pdf.mjs`가 PDF를 쓰기 전에 쪽 상자마다 내용이 상자를 넘쳤는지 본다. 넘쳤으면 어느 덩어리인지 출력하고 실패하며, `out/portfolio.pdf`를 남기지 않는다. 넘친 글은 PDF에서 소리 없이 잘려 나가기 때문에 이것만은 둔다.

**만들지 않는 것**

- 요점과 한 줄 요약의 숫자를 자세한 글과 맞춰 보는 테스트
- 요점의 개수와 줄 수, 그림 크기를 재는 확인
- PDF 쪽 수 확인. 쪽 상자 높이가 고정이라 쪽 수는 구조로 정해진다
- 덩어리 id 중복과 그림 파일 유무를 보는 테스트

이것들은 PDF를 뽑을 때마다 10쪽을 직접 열어 보는 것으로 대신한다. 숫자는 요점을 쓰거나 고칠 때 바로 옆의 자세한 글과 눈으로 맞춘다.

`lib/data.test.ts`에서 바꾸는 테스트는 다음과 같다.

| 지금 테스트 | 처리 | 근거 |
|---|---|---|
| "홈·PDF 목록은 사례가 있는 프로젝트만 중복 없이 가리킨다" | 홈 부분은 남기고, PDF 부분은 `getPdfChunks()`가 던지지 않는지 보는 것으로 바꾼다 | PDF 목록의 단위가 덩어리로 바뀐다 |
| "PDF 목록의 사례는 빈칸 없이 다 쓴 것이다" | 지운다 | `getPdfChunks`가 요점과 그림이 없는 덩어리를 받지 않는다 |
| "다 쓴 사례 중 PDF에 없는 것은 웹 전용으로 정한 사례뿐이다" | 지운다 | 다 쓴 사례를 PDF에서 빠뜨리는 실수를 잡던 테스트다. 덩어리를 골라 싣는 구조에서는 빠진 것이 실수가 아니다 |
| "법무관리 프로젝트의 문제에 배포와 인증 흐름 도식이 연결되어 있다" | 새 모양에 맞게 고친다 | 뜻은 그대로다 |

### 6.8 지우는 인쇄 코드

새 PDF는 `@media print`와 `print:` 클래스에 기대지 않는다. 이 코드들은 지금의 PDF(웹 페이지를 인쇄한 문서)를 만들려고 넣은 것이므로, 새 PDF가 동작하면 모두 지운다. 그 결과 사이트 페이지를 브라우저에서 직접 인쇄했을 때의 모양은 관리하지 않는다. 예를 들어 방문자가 사례 페이지를 직접 인쇄하면 메뉴와 푸터가 함께 찍힌다. 사용자가 이렇게 정했다(2026-11-17).

다 지운 뒤에는 `app`과 `components`에 `print:` 클래스가 없고, `globals.css`에 `@media print` 블록이 없어야 한다. 쪽 크기를 정하는 `@page` 규칙은 새 PDF의 것이므로 남는다.

| 대상 | 처리 | 근거 |
|---|---|---|
| `globals.css`의 `@media print` 색 토큰, 본문 11pt, 그림 설명 9.5pt, 인라인 코드 | 종이 범위로 옮긴다 | PDF와 화면 미리보기가 같은 값을 써야 한다 |
| `globals.css`의 `@media print` 나머지(애니메이션 끄기, 캐러셀, `figure` 쪽 나눔, `orphans`·`widows`) | 지운다 | 새 PDF에는 애니메이션과 갤러리가 없고 쪽이 고정이다 |
| `case-study-body.tsx`의 `KEEP_TOGETHER_MAX_CHARS`, `keepTogether`, `print:` 클래스, `break-*` 클래스 | 지운다 | 흐르는 문서의 쪽 나눔을 맞추던 코드다 |
| `diagram-view.tsx`, `zoomable-image.tsx`의 `print:` 클래스 | 지운다 | 같은 이유다 |
| `navbar.tsx`, `footer.tsx`, `skip-link.tsx`의 `print:hidden` | 지운다 | export가 사이트 틀 밖으로 나가서 필요 없다 |
| `export/page.tsx`의 쪽 여백 상자 스타일과 프로젝트별 `@page` | 지운다 | 꼬리말을 쪽 상자 안에 직접 그린다 |
| `generate-pdf.mjs`의 여백 옵션 | 지운다 | 여백은 쪽 상자가 가진다 |

## 7. 순서와 완료 기준

화면이 바뀌지 않는 리팩터링과 PDF 변경을 섞지 않는다. 단계마다 따로 확인하고, 커밋도 나눌 수 있게 한다.

### 0단계: 화면이 바뀌지 않는 리팩터링

하는 일은 데이터를 새 모양으로 옮기고(6.1), 그림 연결을 바꾸고(6.2), 이를 읽는 코드와 지금 있는 테스트를 맞추는 것이다. 요점은 아직 쓰지 않는다. PDF 목록과 export 페이지는 0단계에서 동작이 그대로여야 하므로, 목록을 덩어리 단위로 바꾸는 일(6.3)은 1단계에서 한다.

완료 기준은 다음과 같다.

- 옮기기 전과 후에 덩어리 16개의 제목, 문단, 그림 설명, 대체 텍스트를 뽑아 비교하면 차이가 없다.
- 사례 페이지 7개의 화면과 글이 옮기기 전과 같다.
- PDF가 옮기기 전과 같다(29쪽, 글 동일).
- `pnpm test`, `pnpm lint`, `pnpm build`가 통과한다.
- 6.2의 표에 있는 것이 지워졌다.

### 1단계: PDF

하는 일은 사이트 틀 분리(6.5), PDF 목록(6.3), PDF 문서(6.4), 웹 앵커(6.6), 넘침 확인(6.7), 인쇄 코드 삭제(6.8), 그리고 수 표기 통일과 요점 9개, 새 그림 하나(8절)다. 수 표기 통일은 0단계의 글 비교가 끝난 뒤에, 요점을 쓰기 전에 한다.

1단계는 하는 일이 많다. 안의 순서는 계획에서 정하되 다음을 지킨다. PDF 목록은 요점과 그림이 있는 덩어리만 받는다(6.3). 그래서 목록을 덩어리 단위로 바꾸는 일은 글이 준비된 뒤에 한다. 권장 순서는 사이트 틀 분리, 수 표기 통일, 요점과 새 그림, PDF 목록과 문서, 인쇄 코드 삭제다. 각각 따로 확인하고 커밋을 나눌 수 있게 한다.

완료 기준은 다음과 같다.

- `out/portfolio.pdf`가 10쪽이고, 책갈피에 덩어리 제목 9개가 있다.
- 덩어리 제목을 누르면 사이트의 그 덩어리 위치가 열린다.
- 브라우저의 `/export/`가 PDF와 같은 모습이다.
- PDF 10쪽을 쪽마다 열어 넘침, 줄 수, 그림 크기를 눈으로 확인했다. 글을 일부러 넘치게 해서 넘침 확인이 PDF를 막는 것도 한 번 본 뒤 되돌린다.
- 사이트 페이지의 화면이 그대로이고, 없는 주소로 가면 메뉴와 푸터가 있는 404가 나온다.
- 6.8의 표에 있는 것이 지워졌다.
- 8절의 수 표기 목록이 모두 반영됐다. 목록의 "지금" 표현이 글, 대체 텍스트, 그림 안 글자에 남아 있지 않다.
- `pnpm test`, `pnpm lint`, `pnpm build`가 통과한다.

### 2단계: 웹

하는 일은 나머지 덩어리 7개의 요점을 쓰고(8절), 웹 덩어리 블록을 바꾸는 것이다(6.6).

완료 기준은 다음과 같다.

- 덩어리 16개 모두에 요점이 있고 `points`가 필수 타입이다.
- 사례 페이지 7개가 요점과 접힌 "자세한 과정"으로 보인다. 자세한 글의 문구는 그대로다.
- 요점 없이 문단만 그리는 경로가 지워졌다.

## 8. 글 작업과 승인

요점과 새 그림은 코드가 아니라 글이므로, 사용자 승인을 거친다.

**요점을 쓰는 규칙**

- 그 덩어리의 자세한 글에 있는 내용만 쓴다. 새 사실과 새 숫자를 넣지 않는다.
- 수는 아래 수 표기 규칙대로 쓰고, 자세한 글과 같은 표기로 쓴다.
- 문제 원인, 해결 과정, 결과마다 요점을 3개 이상 쓴다. 상한은 두지 않는다. 덩어리가 한 쪽에 들어가는 만큼이 한도다. 요점 하나는 한두 줄이다.
- 문제 원인에는 증상만이 아니라 원인까지 쓴다.
- 문장은 명사로 끝나는 개조식을 기본으로 한다(예: "배포 ID로 구버전 요청을 이전 슬롯에 30분 라우팅").
- 덩어리마다 초안을 사용자에게 보여 주고 승인받은 뒤 데이터에 넣는다.

**수 표기 규칙: 읽는 대로 적는다**

사용자가 정한 규칙이다(2026-11-17). 사이트의 모든 글에 적용한다.

1. "한, 두, 세 … 아홉"으로 읽는 한 자리 개수는 한글로 쓰고 단위와 띄어 쓴다. 예: 한 곳, 두 화면, 세 유형, 네 개, 다섯 화면, 일곱 건. 수가 명사 앞에 오면 "개"를 빼고(다섯 화면, 세 유형, 네 축), 명사 뒤에 오면 "개"를 붙인다(설정 파일 세 개, 변수 네 개).
2. "일, 이, 삼"으로 읽는 수, 10 이상의 수, 잰 값은 아라비아 숫자로 쓰고 단위를 붙여 쓴다. 예: 1초, 5분 전, 10회에서 1회로, 46%, 326가지, 16개, 11곳, 1만 줄, 0건.
3. 그림 안의 수열과 수식은 숫자로 둔다. `fabric-group-batch-add` 그림의 "add 1번째…5번째", "재계산 1개…5개", "핀 5개 예시"와 이를 옮긴 그림 설명, 대체 텍스트가 해당한다.
4. 이름과 버전은 그대로 둔다(EC2, S3, Vite 8, CKEditor 5, Fabric.js 6, `Brand/600`). 팀 구성 표기("프론트엔드 1·백엔드 2")도 그대로 둔다.
5. 같은 수는 제목, 한 줄 요약, 요점, 자세한 글, 그림 설명, 대체 텍스트, 그림 안 글자에서 같은 표기로 쓴다.

근거는 국립국어원의 답변이다. 수를 한글과 아라비아 숫자 중 무엇으로 적을지는 어문 규범에 정해진 바가 없고 관습에 따른다. 다만 수가 작을 때는 "한 개, 두 개"처럼 고유어로 읽는 쪽이 더 자연스럽다고 한다(온라인가나다 2025. 4. 30., 2026. 3. 17., 2026. 8. 25. 답변). 띄어쓰기는 한글 맞춤법 제43항을 따른다. 한글로 적은 수 뒤의 단위는 띄어 쓰고("한 곳"), 숫자 뒤의 단위는 붙여 쓸 수 있다("11곳").

사람이 판단하는 규칙이고, 테스트로 강제하지 않는다.

- PDF 목록의 순서는 지금 PDF의 프로젝트 순서를 따른다.
- 요점은 명사로 끝나는 개조식으로 쓴다.
- 새 덩어리 id는 `first-load-lcp`다.
- 타입과 필드 이름은 `Chunk`, `chunks`, `points`, `detail`, `figure`다.
- 2단계의 "자세한 과정"은 기본으로 접어 둔다.
- `CodeBlock`, `MetricsCard`와 `code`·`metrics` 그림 종류를 지운다.
- 새 검사는 넘침 확인 하나만 둔다. 나머지는 PDF를 열어 눈으로 확인한다(6.7).
- 요점의 칸 이름은 가이드의 템플릿을 따라 "문제 원인", "해결 과정", "결과"로 한다.
- PDF를 먼저 하고, 웹 사례 페이지는 2단계에서 요점과 접힌 "자세한 과정"으로 바꾼다. 대화에서 제안했고 사용자가 B를 고르며 받아들였다.
- 이 문서는 세 단계를 모두 다루되, 계획은 0단계와 1단계부터 세운다.

**사용자에게 묻는 것**

- PDF에 화면 캡처를 넣을지. 가이드는 프론트엔드라면 앱 화면 캡처가 강점이 될 수 있다고 한다. 지금 설계에는 화면 캡처가 없고, 가진 캡처는 디자인 시스템 4장, WYSIWYG 2장, 촉각 그래픽 4장이다. 답이 없으면 넣지 않는다.
